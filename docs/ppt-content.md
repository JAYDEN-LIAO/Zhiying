## 第 2 页：Cerno 是什么

**布局：** 上半部分一句话定位（大字居中），下半部分两个并排卡片。

**定位语：** 一个完全本地部署的视频理解与检索系统——自动摘要 + 自由搜索。

**左卡片——视频内容智能摘要：**
上传视频 → 自动输出结构化摘要（一句话概括 + 场景级描述 + 关键词 + 主题 + 实体）。四级摘要质量可升降——默认零成本 Python 聚合器，可按需升级到 DeepSeek V3 / R1 / 本地部署 LLM。

**右卡片——视频内容自由检索：**
用自然语言搜索视频中的任意片段。输入"穿黑色夹克的人"，返回秒级精确定位 + 相似度排序。3 路并行检索（帧级 1fps + chunk 滑动窗口 + 文本语义）互补覆盖。

**旁白：** 两大能力解决两个问题——"这个视频讲了什么"和"视频里哪里有那个东西"。前者是摘要，后者是搜索，共享同一套底层编码。

## 第 4 页：Twelve Labs — 行业标杆，我们的决策起点

**布局：** 上半部分 Twelve Labs 能力拆解（要点列表），下半部分"它如何影响了我们三个关键决策"（因果箭头串联）。

**Twelve Labs 是什么：** 视频语义搜索的行业标杆。核心产品：Marengo 多模态嵌入模型（512 维，专有）+ Pegasus 1.2 摘要模型。仅云 API 部署，按分钟 + 按查询双重计费。优势是产品成熟、嵌入效率高（512 维仅为 Cerno 2048 维的 1/4 存储），劣势是数据必须上传、无法本地部署、不可定制。

**这个竞品直接影响了我们三个关键决策：**

**决策一：Embedding 选型。** Marengo 是专有 512 维嵌入——我们没有自研专有模型的条件。但开源生态给出了更好的答案：Qwen3-VL-Embedding-8B，MMEB-V2 总分 77.8 排名第一，视频子项 67.1 断层领先。代价是 2048 维 vs 512 维（4x 存储差距），但 2048 维带来的语义区分度更高。这是一个有意识的选择——精度换存储，当前规模可接受，未来可通过 Matryoshka 降维或向量数据库升级解决。

**决策二：检索架构。** Twelve Labs 走单一路径的混合检索（向量 + 词汇）。我们选择 3 路并行——因为单一 embedding 路径无法同时满足"秒级定位"和"语义覆盖深度"。帧路给精度、文本路给语义、chunk 路给过程语义。三条路按精度分层校准权重。

**决策三：摘要方案。** Pegasus 1.2 是专有摘要模型，我们无法复制。所以设计四级升降——核心用开源 LLM（DeepSeek V3/R1）做拼合，默认走零成本 Python 聚合器。质量上限可能不及 Pegasus，但零成本且模型可替换。

**旁白：** Twelve Labs 告诉了我们"视频语义搜索应该做成什么样"，也暴露了"纯云 API 路线的天花板"。我们的选型几乎都是在回答"如何在本地部署约束下做到同等甚至更好的效果"。

## 第 5 页：绝影V3.0 — 最值得关注的国内竞品

**布局：** 上半部分产品快照（左侧基本信息 + 右侧三大引擎 + 能力指标），下半部分"绝影的护城河"分层列表 + "我们的学习与追赶方向"。

**产品快照：** 绝影V3.0 是北京多维视通（中科院自动化所背景，2008 年起与公安部物证鉴定中心等联合成立国内首个"视频侦查技术联合实验室"）推出的公安视频侦查装备。以自研"多维视界大模型"为底座，整合三大引擎：

- **文搜图大模型：** 共享字典（Codebook）跨模态对齐——文本编码层 + 视频编码层 → 共享离散空间 → Gumbel Softmax 匹配 → 对比损失监督训练。支持模糊自然语言检索（"浅色外套""中等体型"等非精确描述自动泛化）
- **REID 大模型：** 基于人体先验结构的自监督预训练——利用海量无标注监控视频 → 骨骼/姿态先验指导预训练 → 20+ 维度细粒度特征融合（姿态、步态、背包、配饰、鞋款）→ 对抗训练增强鲁棒性。换装仍可识别，低光照/遮挡/多角度场景识别率 +40%，可一次性检出 20+ 摄像头下的目标
- **目标检测大模型：** 与文搜图/REID 协同，复杂场景自适应优化，大幅降低误报率

关键指标：60-360 倍速处理（猎影达 500 倍）、80 万张/天图片解析、120 小时视频压缩至 1 小时筛查。2025 年已服务全国 29 支省级公安代表队。

**绝影真正的护城河（不是模型，是生态和积累）：** 绝影属于多维视通"影系列"体系——掠影（视频快采）→ 绝影（极速侦查）→ 猎影（研判指挥，多人协同，500 倍速）→ 汇影（图上作战，GB28181 接入雪亮/天网）→ 火影（火灾专项）。这不是单点工具，是深耕公安十余年的完整产品生态。技战法体系（频次分析/同行人分析/M:N 关联/轨迹分析）、多源硬件接入（DVR/NVR 直连、监控硬盘直读、GB28181）、信创适配（国产芯片+OS）——这些都是 Cerno 短期无法追赶的积累。

**我们可以学习的：** YOLO 检测集成（激活预留的 label 搜索路径）、REID 开源方案调研（OSNet/CLIP-ReID）、文搜图的 Codebook 路线可作为技术储备。

**旁白：** 绝影很强，但它的强来自"公安专项 × 十一年积累 × 闭源体系"。和我们的"通用开放 × 开源灵活 × 架构可扩展"是两条路。不和绝影比公安专项——比的是开放性、灵活性和通用场景覆盖。

## 第 6 页：其他竞品速览 + 差异化定位

**布局：** 上半部分 3 个紧凑卡片（Mixpeek / VideoDB / txtai），下半部分 Cerno 四个差异化锚点。

**Mixpeek（架构最接近的开源参考）：** 多模态提取 pipeline（Whisper + CLIP/SigLIP + Gemini VLM）+ 多阶段检索（RRF/DBSF/加权融合）。与 Cerno 3 路编码思路高度相似。核心差异：Mixpeek 用通用图像嵌入（CLIP/SigLIP）+ 外部 API（Gemini），Cerno 用视频原生嵌入（Qwen3-VL-Emb）+ 本地 GPU（Qwen3-VL-32B MoE）。Mixpeek 证明了 pipeline 路线可行，Cerno 的改进是去 API 化和视频原生编码。

**VideoDB（Agent-first 路线的互补者）：** "视频即数据"理念（See-Understand-Act 循环），Agent 驱动交互。与 Cerno 的声明式 DAG 是不同的设计哲学——VideoDB 适合实时交互，Cerno 适合可配置的批量分析。两者在"视频可查询化"目标上殊途同归。

**txtai（通用框架，非视频专用）：** Apache 2.0 开源的全能型 AI 框架。视频能力仅为多模态功能的延伸——all-MiniLM-L6-v2（384 维）通用嵌入 + BLIP 图像字幕，缺乏场景分割、1fps 帧编码、滑动窗口 chunk 等视频专项设计。它证明了"通用框架套视频"的局限性——视频需要专项优化。

**Cerno 四个差异化锚点：**
1. **全本地 + 全开源** — 唯一同时满足数据不出域 + 不锁定供应商的端到端方案
2. **声明式 DAG** — 新增感知模块只需 Runner + Operation 注册，引擎零改动
3. **3 路并行检索 + 精度分层** — 帧级 1fps > 文本场景级 > chunk 窗口级，互补覆盖
4. **四级摘要升降** — 默认零成本 Python 聚合器，不绑定单一方案

**旁白：** 三张小卡片各 15 秒，差异化四点各 10 秒。重点不是"他们做了什么"，而是"我们的位置为什么和他们不同"。

## 第 7 页：模型选型 — VLM 画面描述

**布局：** 上层是候选池全景（按系列分组列出，每组标注入围或排除及原因），中层是筛选漏斗（全领域 30+ → 三轮筛选 → 短名单 13），下层是短名单内三轮排除 + 最终选择 Qwen3-VL-32B MoE 的四个论证。

**选型叙事：**

VLM（Vision-Language Model，多模态视觉语言模型）是 Cerno 的"眼睛"——它直接观看视频片段，输出对画面内容的自然语言描述。这个模型的描述质量决定了后续所有环节（摘要、文本搜索）的上限。选型目标是：在单 GPU 可部署的约束下，找到视频理解能力最强的开源模型。

**第一步：全领域扫描——这个赛道到底有哪些选手？**

视频相关 VLM 是当前 AI 领域迭代最快的赛道之一，每 3-6 个月就有一批新模型。我们从 2024-2026 年的主要模型家族出发，按系列分组扫描：

**Qwen-VL 系列（阿里巴巴，Apache 2.0 开源）：** Qwen-VL 第一代（2023，首个支持中文的开源多模态模型）→ Qwen2-VL-2B/7B/72B（2024，首次支持视频输入和动态分辨率）→ Qwen2.5-VL-7B/72B（2025，Video-MME 71.6%，帧采样方式输入视频）→ Qwen3-VL-8B/32B（2026，架构升级为 Dense+MoE，**原生视频 120fps 输入**，256K 上下文，新增 Thinking 模式）。整个系列的演进方向是：更大上下文 + 更原生视频理解 + MoE 降本。全部开源 Apache 2.0，中文场景优化最深。

**InternVL 系列（上海 AI Lab，MIT 开源）：** InternVL2-1B/2B/4B/8B/26B/76B（2024，InternViT 视觉编码器，帧采样输入视频）→ InternVL2.5-7B/26B/78B（2025，视觉编码器升级，VideoPASTA 优化后 MVBench 73.8）。26B/76B 级别模型在部分 benchmark 上接近甚至超过同级别 Qwen，但有两个短板：中文优化不如 Qwen（训练数据英文为主），EgoPlan-Bench 帧数扩展性差（不支持 64 帧输入 vs Qwen2.5-VL 的 26.04 分）。7B 级别在单 GPU 可行范围内。

**LLaVA 系列（学术开源，Apache 2.0）：** LLaVA-1.5（2024，仅图像）→ LLaVA-1.6（2024，图像+视频）→ LLaVA-NeXT-Video-7B/32B/72B（2025，视频专项版本）。学术影响力大、开源活跃，但视频 benchmark 成绩普遍偏低——LLaVA-NeXT-Video-7B 的 Video-MME 仅 57.8%，72B 也仅 63.5%，与同期 Qwen2.5-VL-7B 的 71.6% 差距在 8-14 个百分点。这不是"略差"，是代际差距。

**MiniCPM-V 系列（面壁智能，Apache 2.0）：** 注重端侧部署和极致轻量，擅长图像理解，但视频能力不是其核心方向。

**其他值得关注但各有短板的开源模型：**
- **CogVLM2**（智谱，2024）——图像对话能力强，但不开源视频分支
- **DeepSeek-VL2**（DeepSeek，2024）——多模态但视频非重点方向，未参与 Video-MME 评测
- **VideoLLaMA3-7B**（2025）——专门为视频理解设计，帧+音频双模态输入。但在 2025 独立评测中直接出局——"经常无法遵循指令或生成有效输出"
- **VideoChat2**（2024）——视频对话早期标杆，但已停止更新
- **mPLUG-Owl3**（2024）——多模态通用但不专注视频
- **PLLaVA**（2024）——视频 LLM 但评测覆盖不全
- **Phi-3-Vision / Phi-3.5-Vision**（Microsoft，MIT）——轻量级图像理解（4.2B），不支持视频输入
- **Florence-2**（Microsoft，MIT）——视觉基础模型，强于检测和 OCR，但非 VLM（不做开放式画面描述）
- **Molmo**（AI2，Apache 2.0）——图像理解，不支持视频

**商业闭源 API（可对比但不能选用）：**
- **Gemini 2.5 Flash/Pro**（Google）——Video-MME 84.8%（Pro 版，当前 SOTA），原生视频+音频输入，3 小时上下文。但仅云 API，数据出境，大规模下 token 成本不可控
- **GPT-4o**（OpenAI）——Video-MME ~71.9%，但视频通过帧采样实现，API 仅支持约 3 分钟。数据出境，$18/百万 token 输出
- **Claude 全系列**（Anthropic）——不支持视频输入，直接淘汰
- **Qwen-VL-Max**（阿里云 API）——与本地 Qwen 同源但更强，仅 API

**第二步：筛选漏斗——从 30+ 到 13 个短名单**

**第一层（硬性功能筛选）：** 必须支持视频输入。排除所有纯图像模型——Phi-3-Vision、Florence-2、Molmo、LLaVA-1.5/1.6（图像版本）。全领域 30+ → 剩余约 20 个。

**第二层（部署可行性筛选）：** 必须开源 + 可本地部署到单 GPU。排除所有商业 API——Gemini Flash/Pro、GPT-4o、Claude、Qwen-VL-Max。同时排除需要多卡的超大开源模型（初步过滤——后续短名单内再细化显存判断）和已停止更新/评测失败的模型（VideoLLaMA3 评测不合格、VideoChat2 停更）。剩余约 13 个进入短名单。

**第三层（benchmark 验证筛选）：** 必须有 Video-MME 或同类权威视频理解 benchmark 成绩，且成绩在可用范围内。排除未参与主流视频评测或评测覆盖不全的——CogVLM2（无视频分支）、DeepSeek-VL2（未参与 Video-MME）、mPLUG-Owl3（评测不完整）、PLLaVA（同）、MiniCPM-V（视频非重点方向）。**最终短名单 13 个**进入详细对比。

**第三步：短名单内三轮排除 → 最终选择**

短名单 13 个候选列表：Qwen2.5-VL-7B/72B、Qwen3-VL-8B/32B、InternVL2-7B/26B/76B、InternVL2.5-7B/26B/78B、LLaVA-NeXT-Video-7B/32B/72B。

**第一轮硬性排除（5 个，benchmark 差距过大或不可部署）：**

- **LLaVA-NeXT-Video-7B/32B/72B** — 7B 的 Video-MME 57.8%，72B 也仅 63.5%。Qwen2.5-VL-7B 是 71.6%——14 个百分点的差距在视频理解任务上就是"可用 vs 不可用"的区别。三个全排
- **InternVL2-76B / InternVL2.5-78B** — 推理需要多张 A100，单 GPU 不可部署。排除

**第二轮精细对比（剩余 8 个）：** Qwen2.5-VL-7B、Qwen3-VL-8B/32B、InternVL2-7B/26B、InternVL2.5-7B/26B、Qwen2.5-VL-72B。

- **InternVL2-7B/26B、InternVL2.5-7B/26B** — 中文是核心场景但 InternVL 家族中文优化不如 Qwen（训练数据英文为主）；EgoPlan-Bench 帧数扩展性差；26B 已超出单张消费级 GPU 的 FP16 推理能力。四个全排
- **Qwen2.5-VL-72B** — Video-MME ~77%+ 是短名单最高，但 FP16 显存约 144GB，需 4×A100。排除
- **Qwen3-VL-8B** — Video-MME 71.4% vs Qwen2.5-VL-7B 的 71.6%，分数略低但架构升级（原生视频 120fps + Thinking + 256K 上下文）。与 Qwen3-VL-32B 对比：32B 的 Video-MME 74.5%，高出 3 个百分点，但 32B 是 MoE 架构仅 3B 激活——INT4 后约 8GB 就能单卡推理，质量接近 72B 级别（Video-MME ~77%+）但显存需求仅 4.5 分之一。最终的抉择在 Qwen2.5-VL-7B vs Qwen3-VL-8B vs Qwen3-VL-32B：7B/8B 在 71% 水准，32B 在 75% 水准——这 4 个百分点的提升来自更深的语义理解，在复杂场景下（多人交互、暗光、快速运动）差距会放大。且 32B 的 MoE 架构使 INT4 后仅 8GB，单卡可行。

**最终选择——Qwen3-VL-32B MoE，四个核心理由：**

1. **MoE 架构红利** — 32B 参数仅 3B 激活。INT4 后约 8GB 单卡推理，质量接近 72B 级别（Video-MME 74.5% vs ~77%+，仅差 ~2.5pp），显存需求少 4.5 倍
2. **原生视频 120fps** — 这不是帧采样然后拼起来，是模型原生接受视频流，内部做时序编码。帧采样丢失帧间运动信息——"人从坐→站→走"在帧采样下只剩孤立姿态，原生视频保留动作连贯性
3. **Thinking 模式** — Chain-of-Thought 推理，复杂场景下先分析再描述。"会议室里的人在争论什么"——先识别人员、分析表情和姿态、判断情绪、理解对话关系，最后输出描述，准确率显著高于直接输出
4. **20+ 分钟连续理解** — 长会议、监控录像不需要切分再拼合，模型原生处理长视频

**旁白：** VLM 选型的核心是从 30+ 候选到 1 个选择的完整筛选链。每个阶段筛掉一批，每个"为什么排掉"都有硬理由。最终 Qwen3-VL-32B MoE 的论证不是"它最好"——是"在单 GPU 约束下，它是综合最优"。

## 第 8 页：模型选型 — Embedding 向量编码

**布局：** 上层是候选池全景（按系列分组，标注各组与 Cerno 需求的匹配度），中层是筛选漏斗（全领域 30+ → 三层筛选 → 短名单 10），下层是短名单内三层排除 + MMEB-V2 对比 + 2B vs 8B 决策。

**选型叙事：**

Embedding 是整个系统最关键的模型决策——它直接决定搜索质量的下限。VLM 描述不准确最多影响摘要质量；Embedding 不好，搜索直接不可用——"搜得到"和"搜不到"的区别。选型目标是：在三模态统一（同一模型同时支持图像、文本、视频编码）的前提下，找到 benchmark 成绩最好的模型。

---

**第一步：全领域扫描——嵌入模型赛道比 VLM 更拥挤**

嵌入模型的数量远超 VLM——从经典的 CLIP 到最新专门为视频设计的嵌入模型，这条赛道上模型代际更替极快。按家族分组：

**CLIP/SigLIP 家族（图像+文本，英文为主）：** 这是嵌入模型领域最庞大的家族。OpenAI CLIP（2021）开启了图文对齐范式，后续衍生出几十个变体：OpenAI CLIP（ViT-B/32、ViT-B/16、ViT-L/14、ViT-L/14@336px）、OpenCLIP（LAION 复现，训练数据更大）、MetaCLIP（Meta 改进训练数据筛选）、DFN CLIP（数据过滤网络优化训练集质量）、ConvNeXt-CLIP（视觉编码器从 ViT 替换为 ConvNeXt）。SigLIP 是 CLIP 的重要改进——用 sigmoid 损失替代 softmax 对比损失，batch size 要求更低、训练更稳定，代表模型 SigLIP ViT-SO400M（878M 参数，1152 维）。EVA-CLIP 则是大参数路线——EVA-CLIP-8B（8B 参数）和 EVA-CLIP-18B（18B 参数），18B 已经是嵌入模型中的巨无霸。**这整个家族有一个共同的致命短板：不支持视频编码。** 它们只能 `encode_image(图像)` + `encode_text(文本)`，要做视频只能逐帧编码后 mean/max pooling——丢失帧间时序，且没有视频 benchmark 成绩。

**中文 CLIP 变体：** Chinese-CLIP（阿里达摩院，中文图文数据训练）、AltCLIP（智源，多语言 CLIP）、Taiyi-CLIP（IDEA 研究院，中文优化）。中文场景明显更强，但同样——不支持视频编码。

**Jina Embeddings 系列（多语言+多模态，Apache 2.0）：** Jina CLIP v1（2023，英文）→ Jina CLIP v2（2024，**89 语言支持**，1024 维，支持 Matryoshka 降维——降维 75% 仍保留 99% 性能，这一特性对 Cerno 的存储效率有直接参考价值）→ Jina Embeddings v3（2025，文本专项，8K 上下文）。Jina 的多语言能力在开源嵌入模型中数一数二（89 语言 vs Qwen 的 30+），但同样——**整个 Jina 系列不支持视频输入**。

**BGE 系列（BAAI，文本+多模态）：** BGE-M3（文本嵌入，多语言+稀疏+稠密混合检索）和 BGE-VL（视觉语言，图像+文本但不支持视频）。文本嵌入质量极高，但视觉模型不覆盖视频场景。

**InternVideo2 系列（视频原生，MIT）：** InternVideo2-S2-6B（6B 参数，768 维，原生视频编码，MSRVTT R@1 55.9）。这是为数不多的视频原生嵌入模型——`encode_video(视频路径)` 而不需要逐帧处理，保留了时序信息。但它有一个结构性问题：**只支持 encode_video，不支持 encode_image 和 encode_text**。这意味着如果选它，Cerno 的三条编码路径需要两个以上的模型——InternVideo2 做视频编码，再加一个 CLIP/BGE 做图像和文本编码——不同模型的向量不在同一空间，搜索时无法直接比较。

**VLM-based 嵌入系列（最新一代，三模态统一）：** 这是 2025-2026 年新出现的范式——利用 VLM 的多模态理解能力做嵌入。VLM2Vec-V2（2B 参数，图像+文本，不支持视频）和 GME-2B（2B 参数，图像+文本，不支持视频）代表了"用 VLM 做嵌入"的思路，但视频是短板。**Qwen3-VL-Embedding 系列**（2B 和 8B，Apache 2.0，2048 维，30+ 语言，图像+视频+文本三模态统一）是目前唯一同时做到"三模态统一"+"有视频 benchmark 成绩"+"开源"的系列——encode_image + encode_text + encode_video 三个接口，一个模型，同一嵌入空间。

**其他注意但不适用的：**
- **LanguageBind**（2023）——视频+音频+深度+红外+文本多模态嵌入，是最早的多模态统一嵌入尝试之一。768 维。但 2023 年后无更新，性能被新一代模型大幅超越，生态停更
- **VideoCoCa**（Google，2024）——视频+文本嵌入，但闭源未开放模型
- **E5-V**（2024）——文本嵌入 E5 系列的视觉扩展，图像+文本，不覆盖视频
- **ImageBind**（Meta，2023）——六模态（图像/视频/音频/文本/深度/热力图）统一嵌入，学术价值极高，但实际检索性能不如专项嵌入模型，且无视频 benchmark 成绩

---

**第二步：筛选漏斗——从 30+ 到 10 个短名单**

**第一层（功能完整性筛选）：** 必须同时支持视频编码。这是硬门槛——Cerno 有三条编码路径，选一个不支持视频的模型意味着要拼接多个模型，而不同模型的向量空间不可比。这一层直接排除整个 CLIP/SigLIP 家族（包括 20+ 变体）、Jina 全系列、Chinese-CLIP 全系列、BGE 全系列、E5-V、ImageBind。全领域 30+ → 剩余不到 10 个。

**第二层（时效性筛选）：** 必须有 2024-2026 年的权威 benchmark 成绩，且持续维护。排除 LanguageBind（2023 年后停更，无最新 benchmark）、VideoCoCa（闭源，无法验证）。剩余约 6-8 个。

**第三层（三模态统一筛选）：** 优先选择单一模型覆盖三模态的方案。排除 InternVideo2-S2-6B（不支持 image/text 编码，需要额外的图像/文本模型来补，体系不一致）。最终进入短名单的核型候选：**Qwen3-VL-Embedding-2B、Qwen3-VL-Embedding-8B、VLM2Vec-V2、GME-2B**。外加 Qwen3-VL-Emb 系列作为直接的 2B vs 8B 内部对比。

---

**第三步：短名单内三层排除 → 最终选择**

MMEB-V2 benchmark 是当前最权威的多模态嵌入评测，覆盖图像检索、视频检索、文档检索的综合能力。短名单内按此对比：

**功能性排除：** VLM2Vec-V2 和 GME-2B 都是"用 VLM 做嵌入"的代表——思路好但视频是短板——VLM2Vec-V2 视频子项 34.6，GME-2B 视频子项 33.6。而 Cerno 的核心场景是视频检索。这个差距不是"略差"——视频检索的 34 分意味着 top-10 准确率极低，在实际产品中就是"搜不到"。

**性能对决：** 排除后只剩 Qwen3-VL-Embedding 家族。MMEB-V2 总分：2B 总分 73.2 / 视频子项 61.9 → 8B 总分 **77.8（总分第一）** / 视频子项 67.1。8B 在所有 embedding 模型中排名第一——不是"同类中最好"，是"当前所有已知模型中最好"。视频子项 67.1 对竞争对手的 34.6/33.6 形成断层——将近 2 倍的差距。

**2B vs 8B 决策：** 2B 总分 73.2 / 视频 61.9，8B 总分 77.8 / 视频 67.1。唯一代价是显存（约 4GB vs 约 16GB）。在这个位置上——embedding 质量决定"搜得到还是搜不到"——这 12GB 值得。

**最终选择——Qwen3-VL-Embedding-8B（2048 维），三个核心论证：**

1. **MMEB-V2 总分第一，无需妥协** — 77.8 分是所有 embedding 模型的总分冠军。不存在"A vs B"的纠结——这就是当前最优，benchmark 可公开验证
2. **视频检索断层领先** — 视频子项 67.1，竞争对手仅为其一半。差距直接转化为 Cerno 搜索结果精度——"搜得到"和"搜不到"的区别
3. **三模态统一，架构简化** — encode_image + encode_text + encode_video 共享一个模型实例。CLIP/Jina/BGE 缺 encode_video，InternVideo2 缺 encode_image/text，LanguageBind 已停更——只有 Qwen 系列能"一个模型覆盖三条路"。三条编码路径共享同一嵌入空间，搜索时不需要跨模型校准

**维度对比（底部 callout）：** Qwen3-VL-Emb 的 2048 维 vs Twelve Labs Marengo 的 512 维——4x 存储差距。当前 demo 规模可接受，未来可通过 Matryoshka 降维（参考 Jina CLIP v2 降维 75% 仍保留 99% 性能的思路）或向量数据库升级解决。

**旁白：** Embedding 选型是全文最有把握的——MMEB-V2 77.8 的公开 benchmark 让选型不存在争论空间。"还有更好的吗？"——当前没有。

## 第 9 页：模型选型 — ASR 语音转录 + 场景分割

**布局：** 上半部分 ASR 双引擎方案（左侧 SenseVoice vs Whisper 关键数据对比，右侧双引擎路由示意），下半部分场景分割选型（6 候选对比 + 选择 TransNetV2 的理由）。

---

**语音转录（ASR）— 双引擎按语言路由：**

语音转录不是 Cerno 的核心差异化模块，选型逻辑相对直接。核心发现：**中文和非中文的最优模型不同，没有一个模型能同时做到最好。**

ASR 领域的候选分两大类：商业云 API（Google/讯飞/阿里等——全本地约束下直接排除）和开源端到端模型。在开源模型中，6 个候选的核心数据如下：

| 模型 | 参数量 | 中文 CER | 倍实时 | 显存 | 语言覆盖 |
|------|:---:|:---:|:---:|:---:|:---:|
| faster-whisper large-v3 | 1.55B | 20.02% | 13.4x | ~6 GB | 99 |
| SenseVoice-Small | 234M | **7.81%** | **169.6x** | **1.6 GB** | 50+ |
| Whisper large-v3-turbo | 809M | 21.71% | 46.1x | ~4 GB | 99 |
| Paraformer-Large | 220M | 10.18% | 119.6x | 3.8 GB | 仅中文 |
| Fun-ASR-Nano | 800M | 8.06% | 17.0x | 1.6 GB | 31 |
| WhisperX (large-v3 + wav2vec2) | 1.55B+ | ~20% | 70x (转录) + 对齐耗时 | ~8 GB | 99 |

排除逻辑很清晰：Fun-ASR-Nano 倍实时 17x 对生产 pipeline 太慢（处理 1 小时视频需约 3.5 分钟转录）；WhisperX 的 ±30ms 词级时间戳能力 Cerno 已有 alignment 模块覆盖，8GB 显存偏高；Whisper turbo 牺牲中文精度换速度（CER 比 large-v3 还差）；Paraformer 中文极强（清晰朗读 CER 仅 2.1%）但训练数据仅 60K 小时中文，非中文完全不可用。

最终选择 SenseVoice-Small + faster-whisper large-v3 双引擎：中文/中英混合 → SenseVoice（2.5x 精度提升，13x 速度提升，省 70% 显存，内置标点恢复和情感检测）；其他语言 → faster-whisper（99 语言覆盖面无可替代）。总显存约 7.6GB。

---

**场景分割 — TransNetV2，传统方法中最优：**

6 个候选分三档：(1) PySceneDetect（Content/Adaptive/Threshold 三种算法）——极快纯 CPU 但有致命缺陷：高运动场景误报 +300%（镜头摇动被误切），低帧率场景召回 -40%。Threshold 算法的 F1 仅 0.061，基本等于随机切分。(2) CLIP-based 方案——F1 0.815-0.910 精度最高，但需同时加载 CLIP + Transformer + DINOv2 等多个模型，部署复杂度和显存远超边际改进价值。(3) TransNetV2——3D CNN 架构，F1 0.648，段级召回 0.632，原生支持渐变检测（比 PySceneDetect 精确约 3 倍），30+ FPS。

选择 TransNetV2 的核心理由：场景分割在 Cerno 中服务于下游 caption/embedding，不是最终产品。CLIP 方案 F1 从 0.648 提升到 0.815+ 的边际收益，不值得付出 3-4 个模型的显存和复杂度代价——分割不是系统的瓶颈环节，"够用就行"是合理的工程判断。

**旁白：** ASR 和分割都不是 Cerno 的核心差异化点。选型逻辑直接、数据支持充分，不需要过度展开。

## 第 10 页：模型选型 — 摘要 LLM

**布局：** 上层是候选池全景（分四组：国际商业 API / 国产商业 API / 国产开源权重 / 本地聚合方案），中层是 7 模型横向对比数据，下层是四级升降方案 + 选择论证。

**选型叙事：**

摘要 LLM 的选型逻辑与前面四个模块不同——VLM、Embedding、ASR、分割都必须选一个确定的模型来跑。摘要的定位更灵活：它不需要绑定单一模型，而是可以设计成一个"根据需求和预算可升降的方案链"。所以这个模块的选型目标不是"选出最好的 LLM"，而是"构建最合理的成本/质量阶梯"。

**候选池全景（先看全貌，再定入围标准）：**

大语言模型是当前 AI 领域最拥挤的赛道——候选数量远超 VLM 和 Embedding。我们从三个维度划分候选池：部署方式（API vs 本地）、中文能力（是否优化）、成本结构。

**第一组：国际商业 API（几乎全部排除）：** GPT-4o（OpenAI，$18/百万输出，128K 上下文，Video-MME ~71.9%）、GPT-4o-mini（OpenAI，$4.32/百万输出，128K 上下文）、Gemini 2.5 Pro（Google，Video-MME 84.8% SOTA，但非纯 LLM——它是多模态模型，不单独做文本摘要）、Claude 全系列（Anthropic，不支持视频输入——在 VLM 选型时已排除，这里同理）。这组的共同问题：数据必须出境（OpenAI/Google 服务器在海外），价格极高（GPT-4o 月成本估算 $250 vs 国产方案 $24），不可本地部署。

**第二组：国产商业 API（入围，作为 L2/L3 可选项）：** DeepSeek V3（671B MoE，37B 激活，128K 上下文，￥2/百万输入 + ￥8/百万输出，开源权重可自部署）、DeepSeek R1（671B MoE，128K 上下文，￥4/百万输入 + ￥16/百万输出，开源权重，ROUGE-L 中文摘要 +17.6% vs 通用 LLM）、Qwen-Plus（阿里云，128K 上下文，￥0.80/百万输入 + ￥2/百万输出——价格最低）、Qwen3.7-Max（阿里云，￥12/百万输入 + ￥36/百万输出——国产最高端）、Qwen3-235B-A22B（235B MoE，22B 激活，262K 上下文——最大的开源上下文窗口，￥0.50-3.20/百万输入）。这组的优势：中文优化、价格普遍远低于国际 API、部分开源权重可本地部署。

**第三组：本地可部署的开源模型（入围，作为 L4 选项）：** DeepSeek V3（开源权重，671B MoE 需要一定规模 GPU 集群，但中小模型版本可行）、Qwen3-235B-A22B（开源权重，235B MoE 但仅 22B 激活，单卡或多卡可行）。

**第四组：非 LLM 方案（入围，作为 L1 默认）：** 纯 Python 聚合器——基于 Counter 频率统计 + 去重排序，不调用任何模型，零成本、零延迟、零数据外泄。

**入围候选横向对比（7 个，覆盖 L1-L4 全谱系）：**

| 模型 | 参数量 | 开源 | 上下文 | 输入 (￥/1M) | 输出 (￥/1M) | 中文 ROUGE-L | 长文本一致性 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| DeepSeek V3 | 671B MoE (37B激活) | **开源权重** | 128K | ￥2.00 | ￥8.00 | 良好 | **最优 (+8.7%)** |
| DeepSeek R1 | 671B MoE | **开源权重** | 128K | ￥4.00 | ￥16.00 | **最高 (+17.6%)** | 一般 |
| Qwen-Plus | — | 仅API | 128K | **￥0.80** | **￥2.00** | 好 | 好 |
| Qwen3-235B-A22B | 235B MoE (22B激活) | **开源权重** | 262K | ￥0.50-3.20 | ￥0.70-13.00 | 好 | 好 |
| Qwen3.7-Max | — | 仅API | 128K | ￥12.00 | ￥36.00 | 优秀 | 好 |
| GPT-4o | 未公开 | 仅API | 128K | ￥18.00 | ￥72.00 | 优秀 | 好 |
| GPT-4o-mini | 未公开 | 仅API | 128K | ￥1.08 | ￥4.32 | 中 | 一般 |

**成本阶梯（以每百万输出 token 价格排序）：**

```

```

**真实月成本估算（每天 10K 次摘要，每次约 3000 input + 500 output tokens）：**
GPT-4o ~$250 vs DeepSeek R1 ~$50-150（含 thinking tokens）vs DeepSeek V3 ~$24 vs GPT-4o-mini ~$15 vs Qwen-Plus ~$6.70。

**第一轮排除——数据出境 + 不可自部署：** GPT-4o（月成本 $250 是 DeepSeek V3 的 10 倍、数据出境、不可自部署）、GPT-4o-mini（成本可接受但中文摘要质量中等——ROUGE-L 低于所有国产模型，数据出境问题同 GPT-4o）、Gemini 2.5 Pro（非纯 LLM，其 SOTA 多模态能力体现在"直接看视频做摘要"的端到端场景，不是"读 caption 文本做拼合"的 Pipeline 场景——与 Cerno 的技术路线不匹配）。

**第二轮排除——性价比或开放性不足：** Qwen3.7-Max（￥36/百万输出，接近 GPT-4o 的价格水平，但开源生态不如 DeepSeek）、Qwen3-235B-A22B（262K 超长上下文是优势但摘要场景通常不需要 128K+；API 定价模式不稳定——输入 ￥0.50-3.20 的范围波动太大，不适合做成本预估）。

**最终方案——四级升降，不绑定单一模型：**

| 级别 | 方案 | 每百万输出成本 | 适用场景 | 选择理由 |
|:---:|------|:---:|------|------|
| **L1 (默认)** | 纯 Python 聚合器 | **￥0** | 日常会议、课程视频、通用视频 | 零成本、零延迟、零数据外泄。遍历所有场景的结构化 caption JSON → Counter 频率统计 → 去重排序 → 输出 VideoSummary。对大多数视频已足够 |
| **L2 (主力)** | DeepSeek V3 API | **￥8** (0.11x GPT-4o) | 需要高质量跨场景推理的摘要 | 中文摘要质量优秀、128K 上下文、开源权重可自部署、价格仅为 GPT-4o 的 1/9 |
| **L3 (高质)** | DeepSeek R1 API | **￥16** (0.22x GPT-4o) | 复杂推理场景（需要因果关联多场景） | ROUGE-L +17.6% vs 通用 LLM，R1-0528 版本幻觉率已降低 45-50% |
| **L4 (全隐私)** | 本地部署 DeepSeek V3 | GPU 成本 | 政府/军工等隐私要求极高的场景 | 开源权重，完全离线，零数据外泄 |

**Qwen-Plus 的角色——成本最优的备选：** ￥2/百万输出（仅为 DeepSeek V3 的 1/4），不适合做 L2 主力（中文摘要 ROUGE-L 低于 DeepSeek V3，且无开源权重不可本地部署），但适合大批量粗摘要场景。

**为什么最终是 DeepSeek 而不是 Qwen 系列做主力：** Qwen-Plus 价格最低但仅 API 无开源、中文摘要质量不如 DeepSeek V3。Qwen3.7-Max 质量优秀但价格接近 GPT-4o，性价比不如 DeepSeek V3。Qwen3-235B-A22B 有 262K 超长上下文但定价不稳定。DeepSeek V3 在中文质量、价格、开源可部署三个维度上没有明显短板——这是它成为 L2 主力 + L4 本地部署底座的原因。

**旁白：** LLM 选型的本质不是"选哪个模型最好"——是构建一个"从零成本到最高质量"的阶梯，让用户根据需求和预算自己选择。DeepSeek V3 在三个关键维度（中文质量/价格/开源）上没有短板，是阶梯的最佳锚点。

## 第 12 页：工作流编排 — 灵活、可扩展的声明式架构

**布局：** 上半部分用通俗的图示表达"用户选择 → 系统自动编排 → 并行执行"的概念（不需要画技术架构图，画一个有亲和力的流程示意），下半部分"这个设计的灵感来源"（3 个来源 + 我们做了什么改进）。

**核心设计理念：声明式——你只需要说"要什么"，系统自己决定"怎么做"。**

传统视频处理系统的工作流是写死的——先分割、再转录、再描述、再摘要，顺序固定，一个环节改了可能牵一发动全身。Cerno 的思路不同：每个处理能力（分割、转录、描述、编码、摘要……）被抽象成一个独立"操作"，操作之间声明"我需要等谁完成才能开始"。用户只需要在界面上勾选想要的能力——比如开启视觉描述和语音转录——系统自动计算哪些操作需要执行、哪些可以并行、哪些有先后依赖。如果某个操作被关闭（例如不启用 OCR），依赖它的下游操作也会自动跳过，不会报错也不会空转。

这带来的直接好处是：(1) **新增能力不影响现有功能**——未来加上 YOLO 检测、REID 追踪，只需要新增一个操作声明，引擎自己把它排进流程的合适位置，已上线的功能不受影响 (2) **参数联动自动校验**——关掉视觉描述，摘要功能会被自动关闭，不会出现"摘要了一个空视频"的尴尬 (3) **能并行的自动并行**——转录和分割互不依赖，自动拆到两条线同时跑，节省等待时间。

**这个设计融合了三个来源的思想，但做了针对性改进：**

- **借鉴 AirFlow / Dagster 的任务编排理念**——任务声明依赖关系、引擎负责拓扑排序和并行调度。Cerno 的关键改进是增加了 Gate 驱动的条件过滤——AirFlow 的 DAG 是静态的（定义了就要执行），Cerno 的 DAG 根据用户在参数面板上的开关动态裁剪。关掉的不执行，也不阻塞后续流程。

- **借鉴 Kubernetes 的声明式配置思想**——YAML 描述期望状态，控制器负责调谐。Cerno 将其从"期望状态"借用到"期望参数"——用户在 4 级参数系统中描述"我期望的处理方式"，引擎负责自动编排出对应的操作序列。

- **借鉴微服务的插件化设计**——接口与实现分离，运行时动态加载。Cerno 每个处理能力都遵循统一的接口规范（8 个抽象基类），模型实现通过配置文件切换（一行 YAML 就能从本地 Qwen 切到 API），操作自己声明需要哪些插件，引擎自动加载。

**对比竞品的工作流设计：** Twelve Labs、Mixpeek 的 pipeline 是固定的产品功能集——你能用他们预设的能力组合，但无法自定义流程。绝影V3.0 推测也是固定 pipeline（三大引擎串联），新增一种分析能力大概率需要改产品代码。VideoDB 走 Agent 驱动路线——把决策交给大模型推理，灵活性最高，但行为不可预测、结果不可复现。Cerno 的声明式 DAG 位于两者之间：比固定 pipeline 灵活，比 Agent 驱动可控。

**旁白：** 声明式 DAG 是整个系统最底层的架构决策。它的价值不在当下——10 个操作用写死的方式也能跑——而在于未来每次新增能力时不需要重构。这是为长期扩展买的保险。

## 第 13 页：方案链对比 — 视频摘要（上）：三大技术路线

**布局：** 三大路线横向对比——每条路线用流程图表示"从原始视频到摘要输出"的完整链路。上方是路线图，下方是各自的优劣和代表产品。

**路线一：端到端（End-to-End）**

原始视频 → [一个巨型多模态模型] → 摘要文本。

代表产品：Gemini 2.5 Pro（Google，Video-MME 84.8% SOTA，3h 上下文，$1.25-2.50/百万 token 输入）、GPT-4o（OpenAI，Video-MME ~71.9%，~3 分钟 API 限制，$18/百万 token 输出）。

优势：架构极简，短-中视频质量最高，不需要前置处理。Gemini 的 84.8% 是目前所有方案中绝对 SOTA。

致命缺陷：(1) 仅云 API——数据必须出境 (2) token 成本极高——1 小时视频的 token 量轻松破百万，极大规模不可持续 (3) 上下文窗口硬上限——GPT-4o 约 3 分钟视频，Gemini 虽支持 3 小时但长视频仍需切分 (4) 闭源不可替换。

**路线二：Pipeline（管道式）**

原始视频 → 场景分割 → 逐场景 VLM Caption → LLM/聚合器拼合 → 结构化摘要。

代表产品/论文：NVIDIA LVS（30-60s chunk → VLM 描述 → CA-RAG 聚合 → JSON events）、Video-RAG（NeurIPS 2025，FastAPI + Streamlit + Whisper + ChromaDB + LangChain）、Cerno。

优势：(1) 管道式可无限扩展——不受上下文窗口限制，长视频天然友好 (2) 成本可控——VLM 推理用本地 GPU，LLM 拼合可选零成本聚合器 (3) 结构化输出——每阶段都有中间结果，可审计可调试 (4) 模型可替换——VLM/LLM/分割每个环节都可独立替换。

劣势：(1) 依赖前置分割质量 (2) 多模型编排增加工程复杂度 (3) 短-中视频质量可能不如端到端（但长视频已反超——见下文）。

**路线三：混合方案（Coarse API + Fine Local）**

粗粒度用 API（如 Gemini 快速过一遍全视频）→ 细粒度用本地方案（在关键片段做深度分析）→ 融合。

代表方案：GenS。优势是兼顾端到端的全局理解和 Pipeline 的细粒度控制。劣势是架构复杂，依赖多供应商。

**关键学术证据：Pipeline 在长视频上已反超端到端。**

Video-RAG（NeurIPS 2025）实验证明：配合 72B 级别模型的 Pipeline 方案在长视频摘要上可以超越 Gemini-1.5-Pro 和 GPT-4o。这不是理论推测——是有实验验证的结论。这意味着 Pipeline 路线不仅在成本和隐私上好于端到端，在长视频质量上也可能是更好的选择。

**Cerno 的路线选择：Pipeline。** 原因：(1) Video-RAG 的核心结论——Pipeline 在长视频上质量可反超端到端 (2) 本地部署硬约束——端到端路线的所有代表产品都是云 API (3) 成本——默认零成本聚合器，端到端路线的 token 费用不可接受 (4) 结构化——Pipeline 天然产出场景级中间结果，这是纯端到端做不到的。

**旁白：** 这一页的核心信息：不是"我们喜欢 Pipeline"所以选 Pipeline——是有学术证据 + 工程约束 + 成本分析三重支撑的决策。

## 第 15 页：方案链对比 — 视频搜索（上）：四种检索范式

**布局：** 四种检索范式横向对比——每种范式用流程图表示"从查询到结果"的完整链路，标注代表产品。

**范式一：统一嵌入 + 单路检索**

用户查询 → [统一 Embedding 模型 encode_text] → 单一向量空间检索 → 排序 → 结果

代表产品：**Twelve Labs**（Marengo 512 维嵌入，向量 + 词汇混合检索）。Twelve Labs 的 Marengo 将视觉、音频、文本统一映射到同一个 512 维空间，单次查询在一个空间中完成。这是最简洁的方案——架构简单、工程成熟。但单一路径无法区分精度层级：一个"穿黑衣服的人"的查询，Marengo 可能返回整个场景（粒度粗），也可能返回具体帧（粒度细），但用户无法控制精度，系统也不区分。

**范式二：共享字典跨模态对齐 + 双侧塔**

用户查询 → [文本编码器] ↘                                    ↘ [ANN 检索] → 结果
                          共享字典（Codebook）→ 离散空间对齐
                       ↗ [视频编码器]（离线预编码）           ↗

代表产品：**绝影V3.0 文搜图**（基于专利 CN113360683A 的共享字典跨模态表示学习）。核心思路：文本和视频各自走独立的编码器，映射到同一个离散空间（共享字典，如 1024 个基向量），Gumbel Softmax 匹配选出最相似的基向量，对比损失训练对齐。双侧塔架构天然支持 ANN 检索，适合大规模。优势在于公安封闭目标集（人、车、物）上可以针对性优化——Codebook 可以在公安数据上专门训练，基向量对"黑色夹克""棒球帽"等公安高频描述更敏感。但代价是 Codebook 需要专门训练，模型不可替换，切换到新场景（如媒体资产管理）需要重新训练 Codebook。

**范式三：多模型拼接 + 多阶段融合**

用户查询 → [通用 Embedding（CLIP/SigLIP）] → 图像级检索
         → [VLM（Gemini API）] → 语义级检索        → [RRF/DBSF 融合] → 结果
         → [ASR（Whisper）] → 文本级检索

代表产品：**Mixpeek**。使用多个来源不同的模型（CLIP/SigLIP 做图像嵌入、Gemini API 做 VLM 理解、Whisper 做转录），各自独立检索后用 RRF（倒数排名融合）或 DBSF（分布式分数融合）合并结果。优势是灵活——每个环节可以独立替换模型。但多个模型不在同一个嵌入空间中，融合时需要归一化和校准，质量损失不可避免。Gemini API 带来数据出境和成本问题。

**范式四：通用框架适配**

用户查询 → [通用 Embedding（all-MiniLM-L6-v2 384 维）] + [BLIP 图像字幕] → 混合检索（向量 + BM25 关键词）→ 结果

代表产品：**txtai**。本质上是一个通用 AI 框架的视频能力延伸——用文本检索的模型做视频检索。384 维嵌入区分度低，BLIP 字幕质量比专用 VLM 差一档，无视频时序建模。它的存在证明了"通用框架套视频"行不通——视频需要原生嵌入和专项设计。

**旁白：** 四种范式的差异本质上是"在哪里做跨模态对齐"的差异。Twelve Labs 在模型内部做（统一嵌入），绝影在共享字典里做（Codebook），Mixpeek 在融合阶段做（RRF），txtai 根本不专门做（直接用通用模型）。

## 第 16 页：方案链对比 — 视频搜索（下）：Cerno 的方案链与五家对比

**布局：** Cerno 的 3 路并行检索流程图（占上半部分），下方是五家方案链对比表 + Cerno 的四个独特优势。

**Cerno 方案链（3 路并行 + 统一嵌入）：**

```
用户查询 "a man in black"
    │
    ▼
[Qwen3-VL-Embedding-8B] encode_text() → 2048-dim 向量（只编码一次）
    │
    ├─ 路 1: 帧级检索 (frame_embeddings 表)
    │   cosine 相似度 × 1.0（金标准权重）
    │   precision_level: "frame"
    │
    ├─ 路 2: Chunk 检索 (chunks 表)
    │   cosine 相似度 × 0.7（编码质量退化）
    │   自适应窗口: ≤5s 不切 / 5-60s 半窗口 / >60s 固定 30s
    │   precision_level: "chunk"
    │
    ├─ 路 3: 文本检索 (scenes.text_embedding)
    │   cosine 相似度 × 0.85（语义可靠但时间粗）
    │   caption + OCR + transcript 三源语义
    │   precision_level: "text"
    │
    └─ 路 4: Label 检索 (scenes.entities JSONB, 预留)
        entities @> [{"label": "person"}]（YOLO 激活后启用）
        precision_level: "label"
    │
    ▼
按 Scene 合并去重
├─ 帧结果按时间聚类（间隔 ≤ 4s 视为同一帧簇）
├─ chunk/text 与帧簇时间重叠 → 丢弃（帧精度更高）
├─ 非重叠结果保留，同 scene 取最高分
└─ 路径感知排序: similarity × path_weight
    │
    ▼
```

**五家方案链对比：**

| 维度 | Twelve Labs | 绝影V3.0 | Mixpeek | txtai | Cerno |
|------|:---:|:---:|:---:|:---:|:---:|

| **精度分层** | ❌ | ❌ | ❌ | ❌ | **✅ 三级** |

| **模型可换** | ❌ | ❌ | 部分 | ✅ | **✅ 换 embedding 即可** |
| **Benchmark 验证** | 复合 78.5% | ❌ | ❌ | ❌ | **MMEB-V2 77.8** |

**Cerno 方案链的四个独特优势：**

**1. 精度分层——不同精度的结果互补而非相互替代。** 帧路给 1fps 秒级定位（最高精度，权重 ×1.0），文本路给 scene 级语义覆盖（caption+OCR+transcript，权重 ×0.85），chunk 路给过程语义（原生视频编码保留时序动态，权重 ×0.7）。用户搜"穿黑衣服的人"——帧路精确定位到 12:03 那一帧，文本路补充"会议室里穿黑色西装的男性"的语义上下文，chunk 路覆盖"他从门口走到座位"的动态过程。如果是 Twelve Labs 的单一路径，这三个维度会混在一起，用户无法区分。

**2. Scene 感知合并——帧簇优先，文本补缺。** 帧结果按时间聚类（≤4s 间隔合并），形成帧簇。chunk/text 结果如果时间与帧簇重叠，直接丢弃——因为帧精度更高，保留反而混淆。非重叠的 chunk/text 结果保留（这些区域没有帧级匹配，但文本语义可能有覆盖）。同 scene 内多个结果取最高分。最终输出按 similarity × path_weight 排序。这个策略比 RRF 或简单的加权求和更适合视频——因为视频有时间维度，帧簇、chunk 窗口、scene 的时间范围有天然的包含关系。

**3. 路径权重校准——可验证、可调整。** frame ×1.0 > text ×0.85 > chunk ×0.7，这个排序不是拍脑袋——有实验支撑：frame embedding 直接编码原始帧，质量损失最小；text embedding 编码的是 caption/OCR/transcript，经过了一层 VLM 转述，质量有损耗；chunk encoding 经过了 480p 降分辨率和 5fps 降帧率预处理，质量损耗最大。权重差距是可调的——如果后续换了更强的 chunk 编码模型，权重可以上调。

**4. 模型可替换——对整个方案链而非单个环节。** 绝影的 Codebook 方案换 embedding 模型就要重新训练 Codebook。Cerno 的方案链里，embedding 模型只是 3 路查询的入口——换一个模型（如 Qwen3-VL-Emb 的下一代）只需改一行配置，3 路检索路径完全不变。

**与绝影文搜图的路线对比（特别标注）：** 这是 Cerno 和绝影在"视频搜索"这个功能上最核心的决策分歧。绝影走的是传统跨模态路线的深化——独立编码器 + 离散空间桥接，适合专业场景的封闭目标集；Cerno 走的是模型能力驱动路线——依赖 Qwen3-VL-Emb 的原生多模态能力做统一空间，简洁且质量可验证。两种路线目前没有绝对的优劣——绝影的方案在公安场景有数据优势（Codebook 可以在公安监控数据上微调），Cerno 的方案在通用场景有灵活性优势。未来如果统一嵌入路线持续进步（MMEB-V2 得分继续提升），Codebook 路线的边际优势会减小。

**旁白：** 3 路并行的本质是承认"没有一种 embedding 能同时做好秒级定位、语义理解和过程刻画"。与其找一个中庸的万能路径，不如三条专业路径各司其职，在结果层做智能合并。

## 第 17 页：三级索引体系 + 4 级参数系统

**布局：** 上半部分用三个卡片并排展示三级索引各自解决了什么问题（不用画技术流程图，用"问题 → 方案"的卡片），下半部分是 4 级参数系统的层级图（金字塔形）。

**三级索引体系——三种互补的视频搜索方式：**

视频搜索的本质困难是"精度"和"语义"往往不可兼得。一个嵌入向量如果擅长精确定位到某一秒（帧级），通常就不擅长理解跨场景的语义脉络（文本级）；如果擅长理解语义，通常就无法做到秒级定位。Cerno 的做法是不追求一个万能的索引，而是建三套互补的索引，各司其职：

**第一级——画面索引（帧级，最高精度）：** 把视频每秒提取一帧，每帧都编码为一个向量。搜索时，查询向量直接在帧向量库中匹配，能精确到具体哪一秒出现了目标。这是最直观的"搜画面"——适合"穿黑衣服的人""红色轿车"这类视觉特征明确的查询。精度最高，置信度也最高。

**第二级——内容索引（文本级，语义最深）：** 把每段场景的描述文字、OCR 识别出的屏幕文字、语音转录的文字——三源文本合并，编码为一个向量。搜索时，查询文本和这些内容文本做语义匹配。这是"搜语义"——适合"讨论预算的会议""提到截止日期的片段"这类需要理解上下文而非匹配像素的查询。时间精度以场景为单位（通常几十秒到几分钟），但语义覆盖深度最高。

**第三级——过程索引（chunk 级，保留动态）：** 将连续几秒的视频片段直接编码为一个向量（而非拆成逐帧），保留了帧间的运动信息和时序动态。这是"搜过程"——适合"有人从座位站起来""车辆转弯"这类需要捕捉连续动作的查询。它填补了帧级索引（只看单帧，不知道前后帧关系）和文本级索引（依赖文字描述，动作可能未被文字覆盖）之间的空白。

三级索引共享一个 Qwen3-VL-Embedding-8B 模型——不需要加载三个不同的嵌入模型。搜索结果按照"帧级优先、文本/chunk 补充"的策略自动合并，用户不需要选择用哪一级索引。

**与竞品索引体系的关键差异：** Twelve Labs 的 Marengo 是单级统一索引——一个向量空间同时覆盖视觉和语义，粒度不可控。绝影V3.0 只有一个检索入口（文搜图），未公开是否有多级索引。Mixpeek 用多模型拼接的方式模拟多级索引（CLIP 管图像、Gemini 管语义、Whisper 管文本），但三个模型不在同一个嵌入空间里，合并结果时需要额外的校准和归一化，质量有损耗。Cerno 的三级索引共享一个嵌入模型，向量在同一个空间中可比，合并时不需要跨模型校准——这是三模态统一嵌入的架构红利。

**4 级参数系统——降低使用门槛的级联配置：**

视频分析的参数很多——用什么语言、采样密度多少、场景切换灵敏度和什么程度、是否开启 OCR、摘要详细程度——如果全部平铺给用户，门槛太高。Cerno 把参数分为四级，从上到下逐级细化：

**L1——选场景类型（最直观）：** 用户只需要告诉系统"这是会议录像"还是"监控视频"还是"教学课程"——系统自动填好下面三层的默认值。会议场景默认开启转录和摘要，监控场景默认开启视觉描述和搜索索引，不需要用户懂任何参数。

**L2——开关感知模块（按需勾选）：** 需要语音转录就开 Audio，需要画面描述就开 Vision，需要提取屏幕文字就开 OCR。不开的模块不仅自己不运行，依赖它的下游操作也会自动跳过——关掉 Vision，Caption 和 Summary 自动屏蔽，不会出现"无画面输入却生成了摘要"的错误。

**L3——选择功能路径（关键决策）：** 是否生成摘要、是否建立搜索索引、摘要走哪条路线（默认零成本本地方案 or 高质量 API 方案）。这是对成本和质量的权衡——日常浏览走本地免费路线，重要视频走 API 高质量路线。

**L4——微调高级参数（专家模式）：** 语言、采样帧率、场景切换灵敏度、是否携带上下文做 Caption、摘要详细程度。普通用户不需要碰这一层，高级用户可以在这里微调。

四级之间有关联校验——L2 的开关会影响 L3 的功能可用性，L1 的场景选择会覆盖 L4 的默认值。这套设计的本质是"粗选自动填充细节"，而不是"所有参数让用户从头填"。

**旁白：** 索引体系解决的是"搜什么"——三种索引对应三种搜索需求。参数系统解决的是"怎么处理"——四级级联让不同水平的用户都能用，新手选 L1 就够了，专家可以深挖到 L4。

**近期能力补齐（3 个月内可完成）：**

**以图搜图。** 当前 Cerno 仅支持"以文搜图"——用文字描述搜索视频。补齐"以图搜图"并不需要新模型：用户上传一张图片 → Qwen3-VL-Emb 的 `encode_image` 编码 → 在 `frame_embeddings` 表中检索最相似帧。同一个模型、同一套向量空间，只是查询入口从文本变成图片。对标绝影的以图搜图能力——他们用 REID 特征做跨镜检索，我们用通用嵌入做相似帧匹配，路线不同但功能对等。

**YOLO 检测 + label 搜索路径激活。** 集成 YOLOv8/YOLOv11，检测结果（标签 + 边界框 + 置信度 + 时间戳）存入预留的 `scenes.entities JSONB` 字段。激活第 16 页描述的路径 4——`entities @> [{"label": "person"}]` 精确匹配。搜索结果中显示检测框选。对标绝影的目标检测引擎——他们用自研检测大模型与 REID/文搜图三联协同，精度差距客观存在；Cerno 用开源 YOLO + JSONB 精确查询，优势在于逻辑透明（100% 精确、零假阳性）、部署轻量、可替换。

**rerank 重排序。** 在 3 路初步检索后增加一个精排层——cross-encoder 对 top-K 候选结果做两两精细匹配，重新排序。目前 Cerno 仅靠 cosine 相似度排序，cosine 对语义相似度的刻画比较粗糙（两个"看起来像但意思完全不同的帧"可能有高 cosine 分）。rerank 层的加入可以用很小的计算代价换取显著的 top-K 精度提升。对标 Twelve Labs 的混合检索 + 排序层——Cerno 的 3 路召回 + rerank 精排构成的"粗排 → 精排"两阶段架构，是信息检索领域验证过的成熟范式。

**chunk 链路正式启用 + 静止帧跳过。** 当前 chunk 编码默认关闭。正式启用后，针对安防/监控场景增加静止画面自动跳过——连续 N 帧无显著像素变化（通过帧差阈值 + 时长阈值判定），直接跳过，不编码 chunk。大幅降低无效编码量，让 chunk 路的性价比从"理论上成立"变成"实际上可用"。这是第 15-16 页方案链对比中第三条检索路径（过程语义）真正落地的关键一步。

**维数截断。** 评估 Qwen3-VL-Emb 的 2048 维向量截断到 1024 维或 512 维后的精度损失。参考 Jina CLIP v2 的 Matryoshka 表征学习——在训练时内置降维能力，降维 75% 仍保留 99% 以上性能。Qwen3-VL-Emb 虽未明确支持 Matryoshka，但可以做维度截断实验验证。如果截断可接受，直接缓解与 Twelve Labs Marengo 512 维相比的 4x 存储差距，也为 pgvector 开启 HNSW 索引（2000 维上限）腾出空间。

**模型升级（短期速赢）。** ASR 升级到 SenseVoice-Small（1-2 天）、VLM 升级到 Qwen3-VL-32B MoE（3-5 天）、Embedding 升级到 Qwen3-VL-Emb-8B（1-2 天）。这三个升级在第 7-10 页模型选型中已有完整论证——选型做完了，模型就绪了，只差执行。

**旁白：** 这一页的每项都有明确的对标对象和时间预期。不是"未来方向"，是"接下来要做的事"。重点传达：近期动作有节奏、有优先级、有对标。

## 第 21 页：中长期升级与深挖（3-12 月）

**布局：** 两大板块。上半部分"生产级改造"（3 项，横向排列），下半部分"深挖方向"（4 项，两列布局），每项标注对标参考和难度。

**主题：让 Cerno 具备生产级可靠性，在对标竞品的核心能力上建立基础。**

---

**生产级改造（让系统可部署、可运维、可扩展）：**

**生产级容错队列。** 当前 pipeline 在内存中异步执行——进程崩溃则任务丢失，无失败重试，无断点续跑。需要迁移到持久化任务队列（如 Celery + Redis 或 ARQ），增加任务状态持久化 + 失败自动重试 + 断点续跑 + 多 Worker 并行。对标绝影宣称的 60-360 倍速处理能力——绝影的高倍速不仅是模型推理快，更是工程调度层面的成熟。速度快的前提是不丢任务、不被单点故障卡死。这项改造技术上不挑战但工程量不小，建议放在中期第一阶段。

**数据库升级。** pgvector 的 2000 维 HNSW 索引上限是硬约束——Cerno 的 2048 维向量只能走 exact scan。当前 demo 规模（数百条视频）不影响体验，但规模化后 exact scan 的延迟会线性增长。评估迁移到 LanceDB（列式存储 + 零拷贝读取，对 embedding 存储有天然优势）或 Qdrant（专用向量数据库，HNSW 无维度限制）。同时在第 20 页维数截断的结果基础上，判断是否需要迁移——如果 1024 维截断可用，pgvector 开启 HNSW 可能就够了。

**模型持续升级跟踪。** 跟踪 Qwen3-VL-Emb 下一代（MMEB-V2 leaderboard 持续刷新）、Qwen3-VL 系列新版本、DeepSeek 本地部署方案成熟度。Cerno 的插件架构使模型替换成本极低——换模型只需改 `config.yaml` 一行，但前提是有人持续跟踪开源模型进展。这不是技术问题，是机制问题——需要建立定期的模型评估和升级节奏。

---

**深挖方向（对标竞品，建立 Cerno 自己的壁垒）：**

**Highlights / 异常检测。** 在监控场景中自动标记异常片段。实现思路不走传统 CV 规则路线（运动检测、背景建模——这些绝影已经做得很深），而是探索 VLM 直接判断——将连续帧组送入 Qwen3-VL-32B，提示"这段画面有什么不寻常的事件发生？如果有，描述它"。VLM 路线的优势是不需要针对每种异常写规则——画面突变、异常行为、目标出现/消失、物品遗留，VLM 天然具备多场景的判别能力。这是对标绝影技战法体系的一个差异化切入——绝影靠规则 + 人工经验，Cerno 靠 VLM 通用理解。可行性需要实验验证（VLM 对监控场景的异常敏感度、误报率），但如果成立，会成为 Cerno 在监控场景的核心卖点。

**REID 跨镜追踪（对标绝影）。** 从开源方案起步——OSNet（轻量级行人重识别，Market-1501 mAP 96.1%）或 CLIP-ReID（基于 CLIP 特征的行人重识别，泛化性好）——作为 Cerno 插件架构下的可选模块。不强求达到绝影自研 REID 大模型的换装识别和 20+ 维度特征融合水平，目标分两步：第一步实现基础跨镜追踪（同一外观下关联多个摄像头下的同一目标），第二步引入开源时序建模提升换装场景的鲁棒性。对标绝影的 REID 引擎——这是 Cerno 差距最大的领域，但开源社区的工具链在快速成熟，追赶的边际成本在降低。

**动态聚档初版（对标绝影）。** 在 REID embedding 可用后，基于时序聚类自动生成目标出现时间线和轨迹摘要——哪个摄像头、什么时间、做了什么（结合 scene caption）。对标绝影的"AI 自动聚类生成人车档案"——他们的动态聚档是完整产品功能（含可视化管理和即时更新），我们第一阶段只做"单个目标的时间线生成"，先有、再全。

**多源接入扩展（对标绝影）。** 从当前仅支持文件上传，扩展到 RTSP 实时流接入（1-2 月），再评估 GB/T 28181 协议兼容的可行性。绝影的多源接入能力（设备直连 DVR/NVR、监控硬盘直读、GB28181）是其公安场景的核心竞争力，背后是十余年的硬件生态和行业协议积累。Cerno 不需要一步到位——先从 RTSP 流开始，让系统能"看"实时摄像头，这意味着从"离线视频分析"扩展到"实时视频分析"，场景从事后检索扩展到实时监控。

**旁白：** 这一页的关键信息是中长期的优先级判断。生产级改造是前提（没有容错就没有生产部署），Highlights 是差异化的突破口（绕开绝影的传统 CV 路线），REID 是最难的但也是对标绝影必须迈过的坎。这四个方向不是并列的——前两个先做，后两个逐步推进。

## 第 22 页：总结

**布局：** 中央一句话定位（最大字号），下方 4 个关键数字 callout 并排，底部总结句。

**定位（大字居中）：** Cerno 是一个完全本地部署的、声明式 DAG 驱动的、3 路并行语义编码的视频理解与检索系统。

**四个关键数字：**

- **10 操作 × DAG** — 声明式编排，新增模块引擎零改动
- **3 路并行检索** — 帧级（1fps）+ chunk（滑动窗口）+ text（caption+OCR+transcript），互补覆盖
- **5 模块全量对比选型** — VLM/Embedding/ASR/分割/LLM，每模块枚举 6-13 候选，逐层排除
- **MMEB-V2 77.8 总分第一** — Embedding 公开 benchmark 可验证，当前无更强模型可选

**底部总结句：**

它融合了 Twelve Labs 的语义搜索产品思路、AirFlow 的 DAG 编排理念、RAG 的多路召回范式、绝影V3.0 的产品化深度参考，在"全本地 + 全开源 + 深度语义搜索"这一交叉点上，目前没有对手站在同一个位置。
